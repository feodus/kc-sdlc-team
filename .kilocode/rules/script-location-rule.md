# Правило расположения скриптов
> **Meta:** v1.1.0 | 15-07-2026
> **Автор:** KiloCode System
> **Источник:** Проектные стандарты

## Назначение
Это правило устанавливает обязательное расположение исполняемых скриптов в проекте KiloCode SDLC. Оно обеспечивает согласованность, обнаруживаемость и разделение ответственности, ограничивая файлы скриптов одной, четко определённой директорией.

## Область действия
Применяется ко всем исполняемым скриптам проекта:
- Оболочечные скрипты (`.sh`, `.bash`)
- Python-скрипты (`.py`)
- PowerShell-скрипты (`.ps1`)
- Батч-файлы (`.bat`, `.cmd`)
- Любые другие исполняемые скрипты автоматизации

## Правило
**Все исполняемые скрипты должны размещаться исключительно в директории `scripts/` в корне проекта** (включая любые вложенные поддиректории внутри `scripts/`). Запрещено размещать скрипты в:
- `src/`, `lib/`, `bin/`, `tools/`, `utils/` и любых поддиректориях
- `.kilo/`, `.kilocode/`, `project_artifacts/`, `tests/`
- Любых других местах вне `scripts/`

Допускается структурировать скрипты по субпапкам внутри `scripts/` для разделения ответственности, например:
- `scripts/validation/` — скрипты валидации (Python)
- `scripts/hooks/` — Git-хуки и вспомогательные скрипты хуков
- `scripts/agents-md/` — скрипты обслуживания AGENTS.md
- `scripts/sync/` — скрипты синхронизации с внешними репозиториями

Скрипт валидации `scripts/validation/validate_scripts_location.py` разрешает любые вложенные поддиректории внутри `scripts/`, но блокирует любые скрипты вне неё.

## Обоснование
1. **Обнаруживаемость** — все скрипты находятся в одном месте, что упрощает поиск и поддержку.
2. **Согласованность** — предотвращает дублирование и разброс инструментов по проекту.
3. **Интеграция с CI/CD** — пайплайны могут надёжно проверять только `scripts/` для хуков и валидации.
4. **Безопасность** — снижает риск неожиданного выполнения скриптов из нестандартных мест.
5. **Целостность структуры проекта** — соответствует модульной и стандартизированной архитектуре KiloCode.

## Предпочтение Python
По возможности создавать исполняемые скрипты только на Python (`.py`) для лучшей кроссплатформенной совместимости с macOS и Linux. Bash/Shell (`.sh`) допустимы для Git-хуков и CI, где это необходимо; PowerShell (`.ps1`) и Bat/CMD (`.bat`, `.cmd`) использовать не рекомендуется.

Рекомендации:
- Отдавайте предпочтение `.py`-скриптам для логики валидации и автоматизации — они запускаются на Windows, Linux и macOS без изменений.
- `.sh`-скрипты оставляйте для Git-хуков (`.git/hooks/pre-commit`) и CI-шагов, требующих оболочку.
- Избегайте создания новых `.ps1`/`.bat`/`.cmd`-скриптов; при наличии Python-эквивалента удаляйте дубликаты.

## Принудительное выполнение
- **Хук pre-commit** — `.git/hooks/pre-commit` должен проверять и отклонять коммиты с добавлением скриптов вне `scripts/`.
- **CI/CD пайплайн** — этап валидации должен аварийно завершаться при обнаружении скриптов вне `scripts/`.
- **Скрипт валидации** — `scripts/validation/validate_scripts_location.py` сканирует репозиторий и сообщает о нарушениях.

## Исключения
- **Временные скрипты**, создаваемые в процессе разработки, могут временно находиться вне `scripts/`, но **должны быть перемещены перед коммитом**.
- **Сгенерированные скрипты** (например, сборщиками) не подпадают под это правило, если они **не коммитятся в репозиторий**.
- **Внешние зависимости** (например, `node_modules/.bin/`) не регулируются этим правилом.

## Примеры
✅ **Разрешено**
```
scripts/validation/check_skill_links.py
scripts/validation/validate_agents.py
scripts/hooks/pre-commit.sh
scripts/hooks/log-params-change.sh
scripts/agents-md/check-agents-freshness.sh
scripts/sync/sync-to-github-universal.sh
```

❌ **Запрещено**
```
src/utils/helpers.sh
bin/deploy.sh
.kilo/scripts/test.sh
tools/build.ps1
.kilocode/rules/check.sh
```

## Связанные артефакты
- `scripts/` — единственное разрешённое расположение скриптов
- `.git/hooks/pre-commit` — обеспечивает применение правила при коммите
- `scripts/validation/validate_scripts_location.py` — скрипт валидации
- `.kilocode/rules/agents-md-management.md` — для смежных стандартов документации
